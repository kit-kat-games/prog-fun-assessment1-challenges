Challenge 1 - Reflection
Context:
This challenge asks me to build an application that uses std::cout to print out a given boat ASCII art. This involved using the std::cout methods for printing to the terminal, and a string holding the ascii art of the boat. From the lectures/tutorials, I already knew how to use the <iostream> standard methods (where std::cout is from).

Action:
Due to being a very simple problem, all I was required to do was find a way to represent the boat and then output this to the terminal. One way of doing this is through a series of std::cout statements outputting each individual line one by one to the terminal, separated by '\n' (newline/std::endl's). However, I decided instead to use a "R-String", also known as an raw string, represented by:
	std::string myBoat = R"(
/////////
/////////
/////////
)";
Where the '/' characters represent the space where the ASCII art is stored. I decided to use this approach as it would allow me to only use a single std::cout statement, by storing the boat art in a single string. I could alternatively have used a standard string which would follow the lines of:
	std::string myBoat = "/////////\n/////////\n/////////\n";
I chose to use the raw string approach, as c++ automatically formats in the newline (\n) characters to match what is written within the program itself. This allowed me to create the ASCII art within the code block, and have a visual representation of what would be outputted into the terminal.

I learnt of raw strings from my lecturer where he suggested the use for an in-tutorial task.

Results:
This use of an R-String worked successfully, and due to the simplicity of the problem, I did not encounter any issues when running my solution.

Learning:
I will continue to apply the use of R-Strings (raw strings) in most cases where ASCII is needed, as it makes constructing them, storing them and referencing them within the program much easier.


Challenge 2 - Reflection
Context:
This challenge asks to build an application which prompts the user for in-game details including name, username, clan tag and current xp number. It then uses input checking to ensure that the inputted data is valid. This application of input checking is the first time I have encountered such a process in c++, and thus I will be learning how to
properly do it in order to account for all edge cases of input. I expect this collection of number input to be the most difficult due to having previous issues with cin within my tutorial tasks.

Action:
I broke the problem down into 3 steps:
Data Collection
Data Manipulation
Data Output

Data Collection for the string variables involved prompting the user with a std::cout statement for what the program expects to recieve next, using getline(cin, stringVarName) to receive terminal input and then putting the inputted text through the following checks:
Checking if the string is empty - If so, output an 'error' message, and prompt the user for input again
Checking each character in the input, and checking whether any are non spaces. If every character is a space, this is counted as invalid and an 'error' message is also outputted, with the user prompted once again. If any character is not a space, we allow the input and continue onto the next variable prompt.

Data Collection for the int variable involved making a temporary string variable that I plan to parse through and ensure it is valid. I chose to use a temporary string variable due to encountering issues when the user would input strings, nothing, or just space characters into the cin prompt. This causes issues that are not consistent between the three of them when attempting to handle the failing input, and thus I believed parsing through the input myself would be the best catch-all solution. This involved using Booleans and looping through the inputted string to ensure there is only a single number present, with no spaces between digits, (no minus signs or decimal points as the number must end up as an unsigned int), but allowing for spaces before and after any present number. Should any invalidity be encountered during parsing, an error message is outputted, and the user is prompted again. If the parsing identifies the input as valid, it is then converted to an integer, and then used in the later steps.

Data Manipulation includes taking the inputted valid data and transforming it into further data we will need to provide the user in the Data Output step. This includes calculating what current level the user is at and deciding the remaining xp points to the next level. For this, I used integer division as it allows me to automatically truncate the value gained by playerXPPoints / xpPerLevel. For example, with 358 XP and 100 xpPerLevel, the result would be 3.58, which is converted to 3 through integer division. I chose to use integer division over manually flooring the value due to it being able to be automatically handled through the division, which reduces the amount of processes, and thus bloat in my program.

Data Output then included outputting this data in the exact format that the assessment required. This involved using simple std::cout (or cout, as I was using namespace std) statements as well as the << operator to properly format the terminal text.

Results:
The input parsing employed in the Data Collection step took a few iterations of solutions to work correctly, however at this point, it works correctly under any edge cases I have given it. It was unexpected the amount of issues I would face when trying to simply use the cin method when trying to input data and check it, however I was able to resolve said issues. I imagine should I research this further, there may be a more efficient or simpler solution to this problem, however given my current knowledge in c++, this is the most appropriate method I have found.

Learning:
This task has allowed me to understand how cin, input parsing and error checking works within a program, as well as the difficulties encountered in doing so. The solutions I designed within this program will likely be very helpful in reusing them within further tasks inside this assessment, my tutorials, and any other c++ projects. I also imagine a similar solution to input parsing could be applied to Task 8 where parsing a command for correct syntax within its command and variables is very important for proper function.


Challenge 3 - Reflection
Context:
This challenge asks me to build a short program where the user inputs a number value, (allowing input of floats and signed numbers). It will then use input checking to ensure the inputted value is valid, and if not, a std::cerr descriptive error message will be output (std::cerr being similar to std::cout, but associated with the standard error stream of C), and a custom error code will be returned. Should a valid input be provided, a variety of values based on this input will be shown to the user (for example, negation, square, rounded values). Due to the similar input parsing within Challenge 2, I was prepared for doing the same process as that assessment's unsigned int checking, but extending the functionality to signed float checking. While this would likely take a little work to cover all edge cases, I did not expect it to be too difficult, and the second part of the problem (calculating and display of values), was not very difficult due to the inbuilt functions within c++.

Action:
This problem was broken down into two steps, input parsing and the data manipulation to display steps, however due to the inbuilt c++ functions, it was realistically only the input parsing step. I used the same approach as assessment 2, with storing the user's input within a string temp variable, looping through each character in their input, and using Booleans and if/else if statements to ensure the formatting of the input is correct. Due to the added allowance of signed values and floats, this parsing was more complicated, including making separate Boolean values for whether the whole and fractional parts of the number have been seen, and ensuring everything is within the correct order, being:
(optional) Negation/Minus Sign
(optional*) Whole Part of Number
(optional*) Decimal Point
(optional*) Fractional Part of Number

Each part is technically optional, due to me allowing difference in input formatting to allow the user some leeway. This includes that they may not impact a signed value or a float, where only a whole part is needed. However, should a float value be inputted, I decided to allow the following input formats to be read, and allowed through the input parsing:
.7 -> 0.7
1. -> 1.0
-.36 -> -0.36
-87. -> -87.0
These formats are readable as said float values, but required specifically storing Booleans on whether its part has been seen (for example, if a decimal point is seen, with no number before), and if not, the left-out '0' character, will be filled in.

Results:
Due to the pre-established input parsing system, this approach worked in only a few iterations of ensuring the parsing order of the float elements was correct. I worked through this with a variety of different values in different formats, where the program worked as expected, providing each input with its proper values.

Learning:
This task has allowed me to refine my understanding of the importance and processing of input parsing within a system that needs user input. The program I have developed here will be helpful for acting as a library input parsing system, where I can use it's functionality to make preset functions for accepting ints or floats, unsigned or signed values, or even multiple different ways of formatting number inputs, such as through the vector input parsing within later assessments, or in a command menu system from Task 8, where inputted numbers act as arguments, and must be filtered through. This will also be an important skill for any project where input validation and manipulation is used, which all games do in some way.

Challenge 5 - Reflection
Context:
This task involves developing a program that will take a string input from the user, and display it in the forms of the following text cases:
Lowercase, Uppercase. Sentence Case, Alternating Case
It also involves parsing the given input to ensure that there is at least one alphabetical character, while still allowing for whitespace within the text to be allowed, as well as numbers. Should an invalid input be given, a warning will be produced. The application of these cases will use the built in c++ functions toupper(char) and tolower(char) in order to produce the expected outputs. It was my first time working with these functions, so I had to work out how to apply them on a whole word, as they are designed for only being used on characters.

Action:
This problem involved the three parts, being data input/parsing, input manipulation, and case output. The case output involves simple std::cout statements and the string input/parsing takes into use the same functionality of string parsing in the previous tasks. For the input manipulation stage, I used a set of for loops for each case, with a loop over each character within the string. For the upper and lower case cases, it involved simply setting the character to its toupper(c) or tolower(c) value. For the alternating case, I kept track of a Boolean for whether the last character was uppercase, if it was, the current character would be set to tolower(c). Finally, for the sentence case, I kept track of every time a terminating type of punctuation was used, ('.', '?', '!') with a Boolean value. When they are seen, the Boolean is set to true. Then the next alphabetical character seen will be set to toupper(c), and the remaining chars of the sentence (until the next terminating symbol) would be tolower(c). This Boolean also began set as true, so the first character given would be set toupper(c). The use of a for loop over the characters of the string is the simplest, and most efficient way to work with the toupper(char) and tolower(char) functions, which were supplied and suggested by both the task, and a lecture.

Results:
The use of the for loops worked as expected, with no issues in the execution and getting the expected results. I tested this using a few forms of invalid input, including inputs with nothing in the string, inputs with only spaces, and inputs with only digits and/or symbols. These cases were all handled as expected and provided a warning in response. I then used a variety of different sentences with different punctuation and word length or counts, and the solution functions correctly in all cases.

Learning:
This task has been helpful in learning the simplest way to apply these cases to the words, which is important within my Assessment 2, as well as any text-based programs and games. This is due to the user not always providing values in expected cases, meaning converting to the format of string we wish to work with in the backend, or output back to the user, is important. These for loops could be built into a custom 'library' header file within a text based game, in order to make an easy macro/solution for applying these cases on strings.

Challenge 6 - Reflection
Context:
This challenge involves a program where the user is prompted for a number between 0-100, and their guess is compared against a randomly generated number within this range. The user is then provided feedback (in the form of a 'hotness' scale, such as freezing for far away, and hot for closer) based on their guess, and allowed to guess a new number. This program will run until the correct number is chosen, where the program will tell the user what the number is, and how many guesses it took them to get to this point. This will involve user input similar to prior tasks, as well as some arithmetic for differentiating the difference between the provided and generated numbers.

Action:
This problem was broken down into three steps, user input (which involved an integer input parsing method like prior tasks, while also checking at the end of the parsing process whether the number is between 0-100, and if not, it is treated as an invalid input with proper feedback), difference calculation and user feedback. This difference calculation involved doing (generated_num - guessed_num), and then applying the absolute value function to the result. This is due to not caring whether we are 5 above, or below the generated number, but simply caring about the distance between the two itself. I then fed this difference into a function with a series of if / else if statements, where different boundaries of difference are checked, and then the appropriate feedback message is outputted using std::cout. The user is then allowed to input a value again. The randomly generated number was produced using the provided header file, using a function called random(lowerBound, upperBound) and producing a value between, inclusively. The game also worked within a pseudo-'gameplay loop', with a Boolean value of whether the gameWon, and if not, the program continues for another guessing iteration. Once the correct guess is given, said while loop will terminate, allowing the program to end.

Results:
This solution worked correctly, with the input parsing method being the only complicated thing within the program, that is already quite dependable due to prior use.

Learning:
The use of a header file in a way that you would use a library file allowed me to strengthen my capability and comfort with using functions this way. The use of a 'gameplay loop' designated by a gameRunning/gameWon variable is also a tool that will likely be used in a decent amount of lower level games not within a game engine, where an update cycle must be hard coded. This allows me to more understand how to do so, should I need to use this tool again in another project.
